# Candidate corpus: real bugs with nondeterministic, file-driven reproduction

Research date: 2026-09-12. Every URL below was fetched and summarised during this session
(via WebFetch or `gh search issues`). "Unverified" marks details I could not confirm from
the page itself. Ranking is by: (a) ease of pinning a tool version, (b) input is a plain
file, (c) nondeterminism is in the *test itself* (not just CI), (d) clear detection signal.

Legend for "Interestingness test difficulty": **Easy** = pinned install + one command +
exit code / grep; **Medium** = needs a build from source, sanitizer build or loop;
**Hard** = no minimal reproducer, or needs heavy environment.

---

## Tier A — set these up first

### 1. Pygments: lexer guessing depends on PYTHONHASHSEED
- **URL:** https://github.com/pygments/pygments/issues/852 (open, labelled S-major)
- **Input:** `test.txt`, one line: `foo bar@email.com` (tiny; inline in issue).
- **Failure:** wrong output — `guess_lexer`/`pygmentize -N`-style detection returns
  RobotFramework (seed=1), Resource (seed=2) or Text (seed=8) for the same file.
- **Nondeterminism:** Python hash randomisation (set/dict iteration order in the lexer
  guessing tie-break). Reproduction rate: depends on seed distribution; issue shows 3
  different answers across seeds 1/2/8.
- **Reproducible today:** issue still open; any `pip install pygments` (pin e.g. 2.4.2
  from 2019 or current). Version not stated in issue — unverified which versions.
- **Interestingness test:** **Easy.** `python -c "from pygments.lexers import guess_lexer; import sys; print(guess_lexer(open(sys.argv[1]).read()).name)" f` and exit 0 iff name != "Text". Do *not* set PYTHONHASHSEED. Nice property: the reducer can also be evaluated against a deterministic run with PYTHONHASHSEED fixed.

### 2. jq 1.6: string multiplication sometimes fails an assertion
- **URL:** https://github.com/jqlang/jq/issues/2192 (closed)
- **Input:** jq filter `".*1024*1024"` on JSON input `"a"` (both a few bytes; the
  *file* under reduction could be the JSON input or the filter file via `-f`).
- **Failure:** `jq: jv_print.c:78: jvp_dump_string: Assertion 'c != -1' failed.`
  (SIGABRT) or wrong output (1046536 vs 1048576 length, NUL bytes in string).
- **Nondeterminism:** uninitialised/garbage memory in string repeat; issue reports the
  first of 10 runs wrong, rest right — rate varies.
- **Reproducible today:** jq 1.5.1 and 1.6 affected; jq 1.6 static binaries are on
  GitHub releases (pinnable). NEWS for 1.7 mentions "Fix string multiplication by 0
  (and less than 1)"; whether 1.7 fixed *this* assertion is unverified — use 1.6.
- **Interestingness test:** **Easy.** Single static binary; check for exit 134 / stderr
  "Assertion". Might need `-n` and a loop of a few runs.

### 3. lark (Earley): parse tree differs with PYTHONHASHSEED
- **URLs:** https://github.com/lark-parser/lark/issues/595 (0.8.5, ~350-line grammar,
  ~10-line input; seeds 4 vs 5 give different trees);
  https://github.com/lark-parser/lark/issues/1434 (1.1.9, 3-char input `a.?` with a
  small ambiguous regex grammar, tree differs run-to-run; PR #1435 referenced);
  https://github.com/lark-parser/lark/issues/1386 (error message "Expected one of"
  order varies; closed not-planned).
- **Failure:** wrong/inconsistent output (tree shape) — detect by comparing
  `tree.pretty()` to a golden or asserting a specific shape.
- **Nondeterminism:** hash-seed-dependent set iteration inside the Earley
  ambiguity resolution.
- **Reproducible today:** `pip install lark==0.8.5` / `lark==1.1.9` pinnable.
- **Interestingness test:** **Easy.** Reduce the grammar file (or input) with the test
  "parse gives the 'bad' tree". Good because grammar files are structured text.

### 4. Z3 5.0.0: SIGSEGV in MBQI model checker, fault site varies per run
- **URL:** https://github.com/Z3Prover/z3/issues/10385 (open; PR #10498 referenced)
- **Input:** SMT-LIB2 file with 15 push/check-sat/pop blocks (floating-point arrays +
  quantifiers), attached as `repro_z3_500_mbqi_segv.smt2` (size not stated).
- **Command:** `z3 -smt2 smt.random_seed=0 rlimit=40000000 smt.arith.solver=6 file.smt2`
- **Failure:** segfault (exit 139) on the 15th check-sat; 3/3 runs crashed but at
  different fault sites (state corruption). 4.16.0 clean.
- **Reproducible today:** z3 5.0.0 release binaries / `pip install z3-solver==5.0.0`
  (PyPI availability of exactly 5.0.0 unverified).
- **Interestingness test:** **Easy** (exit code 139). Note the crash rate at the
  *original* is ~100% but reductions likely make it flaky — good for evaluation.

### 5. Z3 4.12.1: intermittent segfault, ~1 in 10 runs
- **URL:** https://github.com/Z3Prover/z3/issues/6615 (open)
- **Input:** `original.smt2` plus two ddsmt-minimised versions, attached in
  `examples.zip`. Generated by the Dminor refinement type checker.
- **Failure:** segfault, ~1 in 10 executions; minimised versions only crash on the
  platform where they were minimised (Intel mac vs Ubuntu).
- **Reproducible today:** v4.12.1 and commit 25d45a3; pin via GitHub release binaries.
- **Interestingness test:** **Easy** (exit code), but expect a low rate — ideal
  stress test for the nondeterministic-mode statistics.

### 6. Z3: nondeterministic segfault with `qe_rec` (2 of 5 runs)
- **URL:** https://github.com/Z3Prover/z3/issues/3877 (closed, 2020)
- **Input:** small inline SMT2 (`(check-sat-using qe_rec)`, malformed `mod`).
- **Failure:** 2/5 runs segfault, 3/5 print `unknown`. Commit 6e8d900 (April 2020).
- **Reproducible today:** build from that commit (fix not documented in issue).
- **Interestingness test:** **Medium** (source build), otherwise trivial.

### 7. CPython 3.14.6: intermittent SIGSEGV / silent corruption in specialised CALL
- **URL:** https://github.com/python/cpython/issues/155145 (open)
- **Input:** ~30-line pure-stdlib script (inline) looping 2M iterations of nested
  calls with keyword-only args and `math.comb`.
- **Failure:** SIGSEGV, or silent type confusion (floats reading back as strings),
  detected by exit code or an assertion inside the script.
- **Nondeterminism:** fixing PYTHONHASHSEED does *not* make it deterministic —
  allocation-pattern / specialisation-timing dependent. 10 runs gave mixed outcomes.
- **Reproducible today:** 3.14.6 via `uv python install 3.14.6` (deadsnakes in issue).
- **Interestingness test:** **Easy** but each run takes many seconds; timeouts matter.

### 8. CPython 3.12: heap corruption in `re.findall` under allocation load
- **URL:** https://github.com/python/cpython/issues/149692 (closed as not planned)
- **Input:** ~100-line self-contained script; 50k synthetic strings, repeated
  `re.compile().findall()`.
- **Failure:** segfault / "stack smashing detected" / MemoryError-then-segfault;
  "manifestation site is allocator-layout-dependent". Crashes within 20–30 s on
  3.12.13 (python-build-standalone), variable on 3.12.3.
- **Reproducible today:** `uv python install 3.12.13`. Root cause unconfirmed (closed
  not planned) — may be environment-specific; verify before investing.
- **Interestingness test:** **Easy**, slow.

### 9. DuckDB 1.1.2: nondeterministic segfault / wrong answer in read_csv
- **URL:** https://github.com/duckdb/duckdb/issues/14428 (closed; fix PR #14466)
- **Input:** `bug.csv` + SQL `FROM read_csv('bug.csv', header=false, names=['', ''])`.
- **Failure:** segfault, garbage bytes, or wrong column values across runs.
- **Reproducible today:** `pip install duckdb==1.1.2` (pinnable).
- **Interestingness test:** **Easy** — run `duckdb` CLI or python on the SQL file,
  detect exit code or output mismatch. Both the CSV and the SQL are reducible.

### 10. mruby: recursion in `ensure` reads uninitialised memory
- **URL:** https://github.com/mruby/mruby/issues/3423 (closed, fixed Feb 2017)
- **Input:** 8-line Ruby script (inline): recursive `fn(n)` with `ensure`.
- **Failure:** segfault (reliable around n=30) but MSan reports uninitialised reads
  from n>=15 — i.e. for smaller n the crash is layout-dependent. Root cause:
  stale `ci` pointer after `cipop()` reallocation (vm.c ~1702).
- **Reproducible today:** build mruby at a commit before the fix (Feb 2017).
- **Interestingness test:** **Medium** (source build; small C project). Use the
  non-sanitised binary so that failure is genuinely intermittent.

## Tier B — good, more setup or lower rate

### 11. rustc parallel front-end (`-Zthreads=N`): diagnostics flip-flop
- **URL:** https://github.com/rust-lang/rust/issues/142063 (open)
- **Input:** 2-line inline Rust file (`trait A { fn foo() -> A; } trait B { fn foo() -> A; }`).
- **Flags:** `--edition=2024 -Zthreads=8 --crate-type=lib`, nightly 2025-06-04.
- **Failure:** wrong output — sometimes 1 error (E0391 cycle), sometimes 3 (E0782).
- **Reproducible today:** `rustup toolchain install nightly-2025-06-05`.
- **Interestingness test:** **Easy** — grep stderr for E0391. Related ICE on the
  same input: https://github.com/rust-lang/rust/issues/142064 ("entered unreachable
  code", `-Zthreads=2`), reported as deterministic.

### 12. rustc parallel/incremental ICEs (race conditions)
- https://github.com/rust-lang/rust/issues/162316 — "caller raced calls to put()" in
  `vec_cache.rs` (open, PR #162515). Flaky in CI; no minimal reproducer.
- https://github.com/rust-lang/rust/issues/152662 — "stealing value which is locked",
  `-Zthreads=8` + incremental, intermittent across rebuilds (S-needs-repro).
- https://github.com/rust-lang/rust/issues/141540 — "dep graph node ... does not have
  an unique index", sporadic with incremental builds; closed by PR #151509.
- **Assessment:** real races, pinnable nightlies, but **Hard**: no minimal single-file
  reproducer; would need a small crate and repeated incremental builds.

### 13. QuickJS-ng: cycle-GC use-after-free in running async function
- **URL:** https://github.com/quickjs-ng/quickjs/issues/1570 (open, July 2026)
- **Input:** small inline JS (`for await (using r of iterable)` allocating objects).
- **Failure:** SIGSEGV in `gc_scan_incref_child`; "intermittent crashes" in standard
  builds, deterministic with `-DFORCE_GC_AT_MALLOC` or under ASan.
- **Reproducible today:** commit d950d55.
- **Interestingness test:** **Medium** (build qjs; ~1 min). Use the plain build
  for nondeterminism. Excellent because the deterministic build gives ground truth.

### 14. Go 1.23.0: range-over-func miscompile → nondeterministic crashes
- **URL:** https://github.com/golang/go/issues/69507 (release-blocker; backport #69511)
- **Input:** single Go file (playground link go.dev/play/p/rYiGIM4RaVe).
- **Failure:** "concurrent map read and map write" fatal error, SIGSEGV, or panic
  with impossible map keys; disappears when an unrelated print is enabled.
- **Reproducible today:** `go1.23.0` toolchain pinnable via `GOTOOLCHAIN=go1.23.0`.
- **Interestingness test:** **Easy** (`go run file.go`; non-zero exit).

### 15. Lua 5.4.0 / 5.4.3 GC bugs (official bug list)
- **URL:** https://www.lua.org/bugs.html — entries: 5.4.0 "Barriers cannot be active
  during sweep phase" (Yongheng Chen), 5.4.0 "Long string can be collected while its
  contents is being read when loading a binary file" (Payo Nel), 5.4.3 "Finalizers
  can be called with an invalid stack" (Minseok Kang), 5.3.2 "Metatable may access
  its own deallocated field" ("will segfault on some machines").
- **Input:** each has a <20-line Lua script (quoted on the page).
- **Failure:** use-after-free; the page says several only fail "under a memory checker
  like valgrind" — without a checker the crash is layout/ASLR dependent (intermittent).
- **Reproducible today:** lua.org tarballs for 5.4.0/5.4.3/5.3.2 (trivial build).
- **Interestingness test:** **Medium**: use plain build + exit code for a flaky
  signal, or valgrind for a deterministic oracle.

### 16. CPython free-threading: `crashers/mutation_inside_cyclegc.py` hangs / sometimes segfaults
- **URL:** https://github.com/python/cpython/issues/126365 (closed not planned)
- **Input:** `Lib/test/crashers/mutation_inside_cyclegc.py` in the CPython tree.
- **Failure:** hang, occasional SIGSEGV in `visit_decref` (gc_free_threading.c:442);
  `--disable-gil --with-pydebug` build, Nov 2024 main.
- **Interestingness test:** **Medium** (custom build); needs timeout-as-failure.

### 17. SymPy: `hyperexpand` fails only for some hash seeds
- **URL:** https://github.com/sympy/sympy/issues/14481 (open) — also #12870 same title
- **Input:** an expression `hyperexpand(hyper([3],[1,d,e],z))` with random params.
- **Failure:** `PolynomialDivisionFailed` exception under PYTHONHASHSEED=245293771,
  sympy 1.1.2.dev0. Also https://github.com/sympy/sympy/issues/11274 (intermittent
  "Cannot recover from stack overflow" in Wester tests, 2016).
- **Interestingness test:** **Easy** with `pip install sympy==1.1.1`, but the
  reporter's failure also involves random parameters — must freeze those and let
  only the hash seed vary. Unverified rate.

### 18. dask 2026.7.1: optimised graph size depends on PYTHONHASHSEED
- **URL:** https://github.com/dask/dask/issues/12507 (open; PR #12509)
- **Input:** small script (8x10x20 array); task count 348–870 depending on seed;

- **Failure:** wrong output (threshold on task count). Pinnable via pip.
- **Interestingness test:** **Easy**, though "interesting" is a numeric threshold.

### 19. NetworkX `simple_cycles()` ordering depends on set iteration

## Things searched that did NOT yield usable candidates
- GCC Bugzilla is behind Anubis (403 to fetch); `--param ggc-min-expand=0` GC-timing
  ICEs are a known class (see trofi.github.io posts 301/347) but I could not enumerate
  bug IDs. Worth querying Bugzilla interactively with quicksearch `ggc-min-expand=0`.
- oss-fuzz "Reliably reproduces: NO" issues are not indexed by web search; the
  issues.oss-fuzz.com tracker would need direct browsing.
- regehr/compiler-crashes (https://github.com/regehr/compiler-crashes) is explicitly
  *deterministic* crashes, but its README warns to disable ASLR — the 60 GCC/Clang
  crash inputs plus C-Reduce `test1.pl` scripts could be a useful *deterministic*
  baseline, and some may become flaky with ASLR on (unverified).
- LLVM `LLVM_ENABLE_REVERSE_ITERATION` bugs (e.g. https://github.com/llvm/llvm-project/issues/132926)
  are deterministic per-build, not per-run — not suitable.
- CPython bpo-43850 (set order in bytecode depends on hash seed) is only observable
  by comparing two runs — not a per-run oracle.
- wasmtime/wabt/binaryen, ruff, tree-sitter, ImageMagick, qpdf, libvips, ruby,
  ghc: `gh search issues` turned up nothing with a file-driven intermittent crash.
- Academic flaky-test datasets (iDFlakies etc.) were not pursued: they are
  test-suite-level, not single-file inputs.

## The five I would set up first, and why

1. **Pygments #852** — pip install, tiny text input, oracle is one Python call, the
   bug is *purely* hash-seed driven so the failure probability per run is a clean,
   measurable function of the input, and a deterministic baseline is one env var
   away (`PYTHONHASHSEED=1`). Perfect for comparing ND vs deterministic reduction.
2. **jq 1.6 #2192** — single static binary, bytes-level input, assertion abort with
   a distinctive exit code; the intermittency is memory-garbage-driven, i.e. the
   "unknown rate, may change as the input shrinks" regime we most want to test.
3. **Z3 5.0.0 #10385** (with **#6615** as a low-rate follow-up) — a real, attached,
   machine-generated SMT2 file the maintainers already reduced only "at block
   granularity"; pinnable binary; crash rate ~100% on the original but the varying
   fault sites mean reductions will flake. #6615 gives a ~10 % baseline rate.
4. **lark 1.1.9 #1434 / 0.8.5 #595** — structured grammar-file reduction under
   hash-seed nondeterminism; wrong-output (not crash) oracle exercises a different
   detection path, and both grammar and input can be reduced.
5. **QuickJS-ng #1570** — small JS input, C build in ~1 minute, GC-timing UAF that
   is intermittent in the normal build but *deterministic* with
   `-DFORCE_GC_AT_MALLOC`/ASan, giving a ground-truth minimal result to compare
   the nondeterministic reduction against.

Runner-ups: DuckDB 1.1.2 #14428 (pip-pinnable, CSV+SQL both reducible) and CPython
3.14.6 #155145 (uv-pinnable, but each run is slow).
